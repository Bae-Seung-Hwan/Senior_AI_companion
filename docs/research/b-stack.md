## 0. 먼저 정해야 하는 것: 앱 프레임워크

푸시와 인앱결제는 **앱을 무엇으로 만드는지에 따라** 선택지가 달라집니다. 그래서 회의에서는 앱 프레임워크(React Native+Expo / Flutter / 네이티브)를 먼저 정하고, 아래 표에서 고르는 순서를 권합니다.

## 1. 우리 서비스에서 중요한 기준

| 기준 | 왜 중요한가 |
| --- | --- |
| 긴급 알림이 빨리, 확실히 도착 | 사기·응급 알림(명세 4)은 몇 초 안에 보호자에게 가야 함 |
| 보호자가 앱을 안 깔아도 받음 | 자녀가 앱을 설치하기 전에도 카톡으로 요약·긴급 알림을 받아야 이탈이 적음 |
| 민감정보를 외부로 덜 보냄 | 알림톡 본문은 카카오·대행사를 거침 → 건강·대화 내용은 넣지 않음 (#37 리뷰) |
| 시연 일정 | 알림톡은 채널 개설·템플릿 검수에 영업일이 걸림 → 미리 신청해야 함 |
| 2인 팀이 운영 가능 | 직접 만들 것과 맡길 것을 나눔 |

## 2. 앱 푸시

| 후보 | 비용 | 특징 | 비고 |
| --- | --- | --- | --- |
| **FCM** (Firebase Cloud Messaging) | 무료 | Android·iOS 모두 보냄 (iOS는 APNs 경유) | 프레임워크와 상관없이 쓸 수 있는 기본값 |
| **Expo Push** | 무료 (프로젝트당 초당 600건 제한) | Expo 앱이면 설정이 가장 쉬움. 내부적으로 FCM·APNs 사용 | Expo를 고를 때만 |
| APNs 직접 | 무료 (Apple 개발자 연 $99는 어차피 필요) | iOS 전용 | 따로 쓸 이유 적음 |
| OneSignal 등 유료 서비스 | 일정 규모 이상 유료 | 세그먼트·예약·통계 | MVP에는 과함 |

- 세 무료 서비스 모두 **페이로드가 약 4KB로 제한**됩니다. 알림에는 짧은 문장과 ID만 넣고, 내용은 앱에서 서버로 다시 조회합니다
- 예약 발송(복약 알림 #47)은 푸시 서비스가 해주지 않습니다. **서버의 예약 작업이나 기기 로컬 알림**으로 해야 하므로, 서버 스택을 고를 때 예약 작업(스케줄러) 지원을 같이 봅니다

**잠정 추천**: Expo를 쓰면 Expo Push, 아니면 FCM

## 3. 카카오 알림톡 (MVP 이후)

> MVP에서는 쓰지 않습니다 (2026-11-24 합의). 채널 명의·검수 기간 문제가 MVP 일정에서 빠졌습니다.

알림톡은 카카오에 직접 연동할 수 없고 **공식 딜러사(발송 대행사)**를 거쳐야 합니다.

### 준비 절차와 기간

| 단계 | 기간 (2차 자료) | 메모 |
| --- | --- | --- |
| 카카오톡 비즈니스 채널 개설·심사 | 1~3영업일 | 사업자 정보와 **고객센터 연락처**가 필요. 팀 프로젝트라 사업자가 없으면 대행사·학교 쪽 방법 확인 필요 |
| 대행사 가입·채널 연동 | 1일 안팎 | |
| 템플릿 등록·검수 | 2~3영업일 (3~5영업일이라는 자료도 있음) | 검수는 카카오가 하며 대행사가 앞당겨 줄 수 없음. 반려되면 다시 기다려야 함 |

👉 **약 1~2주 여유를 두고 신청해야** 첫 시연에 알림톡을 쓸 수 있습니다. 시연까지 시간이 없으면 **첫 시연은 앱 푸시로만** 하고 알림톡은 뒤에 붙이는 안을 권합니다.

### 대행사 비교

| 대행사 | 건당 단가 (VAT 별도) | 메모 |
| --- | --- | --- |
| 솔라피 | 월 1~9,999건 13원, 1만~10만 건 10원 | 단가표가 공개돼 비교 쉬움, 개발자용 API 문서 |
| NHN Cloud | 요금 계산기로 확인 | 공식 딜러사, 클라우드 다른 서비스와 묶어 쓰기 좋음 |
| 인포뱅크 비즈고 | 5,000건 기준 건당 약 7원 (충전식) | 2026-07 비교 글 기준 |
| 스윗트래커 비즈엠 | 5,000건 기준 건당 약 8원 | 2026-07 비교 글 기준 |

- MVP·베타 규모(월 수천 건)에서는 **어디를 골라도 월 몇만 원 이하**입니다. 가격보다 **API 문서, 테스트 환경, SMS 대체 발송 지원**을 보고 고르는 게 낫습니다
- 알림톡이 실패하면(카톡 미사용 등) **SMS로 대체 발송**하는 기능을 대부분 지원합니다. 긴급 알림(명세 4)에는 켜 두는 것을 권합니다
- **SMS 대체 발송 본문도 알림톡 템플릿과 같은 규칙을 따릅니다.** 문자 본문은 통신사를 거치므로 긴급 알림은 유형과 시각만, 하루 요약은 `brief`와 앱 링크만 넣고 대화 원문·건강·기분 내용은 넣지 않습니다

### 우리 앱에 필요한 템플릿 (미리 검수 신청할 것)

| 템플릿 | 내용 | 관련 이슈 |
| --- | --- | --- |
| 보호자 초대 | "OOO 님이 보호자로 초대했어요" + 수락 링크. **가입 전 보호자의 전화번호가 있어야 보낼 수 있음** (아래 참고) | #40 |
| 하루 요약 | `brief` 한 문장 + 앱에서 자세히 보기 링크 (건강·기분 내용은 넣지 않음) | #48, #50 |
| 주간 요약 (무료 등급) | 주간 한 줄 요약 + 앱 링크 | #52 |
| 긴급 알림 | 유형(사기 의심/응급)과 시각만 + 앱에서 확인 링크 (대화 원문은 넣지 않음) | #49, #50 |

### 보호자 초대는 어떻게 보낼까

알림톡은 받는 사람의 전화번호로 보냅니다. 그런데 초대받는 보호자는 아직 가입 전이라 `users.phone`이 없습니다. 방법은 두 가지입니다.

| 방법 | 필요한 것 | 장점 | 단점 |
| --- | --- | --- | --- |
| **어르신 폰에서 카톡 공유** (초대 링크를 카톡 대화방으로 보냄) | 없음 (카카오 공유 SDK) | 템플릿 검수 없이 바로 쓸 수 있음, 보호자 전화번호를 저장하지 않음 | 어르신이 카톡에서 받을 사람을 직접 골라야 함 |
| 알림톡 "보호자 초대" 템플릿 | 초대할 때 보호자 전화번호를 입력 받아 저장 (#65 `guardian_invites.invitee_phone`) | 어르신은 번호만 말하면 됨 (보호자 원격 설정 #43과도 잘 맞음) | 템플릿 검수 필요, 가입 전 사람의 번호를 잠시 보관 (사용·만료 후 삭제) |

**정함**: MVP는 **카톡 공유**로 합니다 (알림톡을 MVP에서 빼기로 해서). 알림톡 초대는 알림톡을 붙일 때 추가합니다. DB 초안(#65)은 둘 다 되도록 `invitee_phone`을 null 허용으로 두었습니다.

**잠정 추천**: 솔라피 (공개 단가·개발 문서가 명확해서 2인 팀이 바로 쓰기 좋음). NHN Cloud는 서버를 NHN Cloud로 정하면 재검토

## 4. 인앱결제 검증 (#60)

| 후보 | 비용 | 장점 | 단점 |
| --- | --- | --- | --- |
| **직접 구현** (App Store Server API + Google Play Developer API) | 무료 | 외부 의존 없음, 결제 데이터가 우리 서버에만 | 영수증 검증, 갱신·해지·환불 알림(웹훅) 처리를 두 스토어 각각 만들어야 함 |
| **RevenueCat** | 월 추적 매출 $2,500까지 무료, 넘으면 매출의 약 1% (자료마다 차이, 공식 페이지 확인 필요) | 두 스토어를 한 API로, 웹훅·구독 상태 관리 제공, 자녀가 대신 결제하는 흐름에도 유리 | 외부 서비스에 구독 데이터가 감 |

- 베타 기간 매출은 무료 구간 안일 가능성이 높습니다. **MVP는 RevenueCat으로 빨리 붙이고**, 매출이 커지면 직접 구현을 검토하는 안을 권합니다
- 국내 앱이라 **원스토어**나 외부 결제도 나중에 검토 대상입니다 (MVP 제외)

## 5. DB

B 영역 데이터는 서로 **관계가 많고 이력이 중요합니다.**

- 회원 ↔ 보호자 (여러 명), 공유 범위, **동의·철회 이력**(언제 무엇에 동의했는지 지우지 않고 쌓기, #41)
- 할 일·복약 ↔ 알림 예약 ↔ 완료 기록
- 하루 요약 ↔ 보호자별 발송 기록, 긴급 알림 ↔ 발송 기록
- 구독 상태 ↔ 대화 사용량

| 후보 | 맞는 점 | 걸리는 점 |
| --- | --- | --- |
| **PostgreSQL** (관리형: Supabase, AWS RDS, NHN Cloud 등) | 관계·이력 저장에 강함, 트랜잭션으로 중복 방지(`request_id`) 쉬움, 위치 검색(PostGIS)으로 모임 매칭(#54)도 가능 | 서버를 직접 운영하거나 관리형 비용 |
| Firebase Firestore | 앱에서 바로 붙고 FCM과 같은 콘솔 | 관계·이력 조회가 불편, 동의 이력·발송 기록처럼 쌓이는 데이터 비용 예측 어려움 |
| MySQL | 익숙한 팀이면 무난 | PostgreSQL 대비 위치 검색 등 확장 적음 |

**잠정 추천**: PostgreSQL. 2인 팀이면 **관리형(예: Supabase)**으로 운영 부담을 줄이는 안

> 민감정보: 대화·건강 정보를 저장하는 DB는 **국내 리전**과 암호화 지원 여부를 같이 확인합니다.
